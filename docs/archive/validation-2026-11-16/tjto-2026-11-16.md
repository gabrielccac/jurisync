## Correção no conector

`337561d Accept TJTO's mTLS certificate host and report it when unpublished`

- `certificate.require_login_url` rejeitava o redirect para `mtls.tjto.jus.br` (não é host SSO). Mesmo com o DNS
  publicado, o login por certificado falharia com `Unexpected eproc login redirect URL`. Agora o host é aceito só para

  mtls.tjto.jus.br does not resolve (not published in DNS by the court); certificate login is unavailable until it is`.

## CAPTCHA (tarde de 16/11)

O usuário aprovou resolver o CAPTCHA do caminho por senha.

### Como funciona no portal (conta inexistente, não é de cliente)

- Todo POST de usuário/senha em `index.php` cai na tela `hdnStrTela=captcha`, antes de a senha ser checada.
- Cada GET da tela desenha uma imagem nova (não precisa novo POST de senha).
- Código errado: só redesenha a imagem (mesma URL `acao=principal&acao_retorno=login`, sem mensagem de erro de senha).
- Código certo: o portal checa a senha; conta inexistente volta ao login com `msg=Senha ou usuário Inválidos`.
- O envio precisa de `hdnInfraCaptcha=1` (o JS da página põe 1; com 0 o código certo é ignorado).
- A comparação ignora maiúsculas/minúsculas (`f77f` aceito para `F77F`).
- O código não é só de dígitos: 4 caracteres alfanuméricos em fonte serifada, uma cor escura, sobre linhas
  coloridas e fundos variados.

### Implementação

- `src/jurisync/core/image_captcha.py`: `solve(imagem, attempt=n)`. Na 1ª imagem de um login tenta o ddddocr
  (extra opcional `captcha-ocr`), só usando resposta `^[A-Za-z0-9]{4}$`; senão, ou a partir da 2ª imagem, usa o modelo
  de visão (chave `JURISYNC_CAPTCHA_API_KEY`, depois `OPENROUTER_API_KEY`; modelo `JURISYNC_CAPTCHA_MODEL`).
  Resposta fora do formato: pede imagem nova em vez de chutar.
- `eproc/http_login.py`: portais `flavor="infra-captcha"` (tjto-1g/2g) postam a senha em `index.php` (não
  `acao=login_cert`), respondem até 3 códigos (até 6 imagens), depois seguem para o código TOTP e o painel. Senha
  recusada depois do CAPTCHA vira `LoginRejected` (o pool não reenvia). Usuário fora do formato `UF + 6 dígitos`
  é barrado antes de enviar qualquer coisa.
- Teste ponta a ponta com a conta inexistente pelo conector: 4 de 4 logins passaram o CAPTCHA na 1ª imagem, lida
  localmente (3 no 1G, 1 no 2G), terminando em `Senha ou usuário Inválidos`.

### Login real (Dênis)

- 1 tentativa no `tjto-1g`, pelas tools do servidor MCP: o CAPTCHA foi aceito (a recusa de senha só vem depois de um
  código certo) e o portal respondeu `Senha ou usuário Inválidos`. Parado aí, como manda a regra.
- `TJTO_1G_USERNAME` (e `TJTO_2G_USERNAME`, igual) tem 11 dígitos (formato de CPF). A página de login do TJTO diz
  "O login segue o formato: UF + número da OAB com 6 dígitos (ex: TO001234)". Senha de 2G = senha de 1G, então o
  2G não foi tentado.
